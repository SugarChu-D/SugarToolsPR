# GUI から利用する検索の境界

初回の GUI は White 2 の単日 Tepig 検索から始める。CLI と手動検索用テストは、GUI 上で同じ条件を指定して結果を取得できるまで利用を続ける。

| 層 | 責任 |
| --- | --- |
| GUI・CLI | 文字列や選択項目から型付きの入力を組み立て、検索を実行する。進捗、失敗、結果を表示し、選んだ形式で保存する。 |
| `search` | 検索種別ごとの入力と結果を公開する。対象シーズンや性格など、検索固有の制約を確認し、GPU 候補生成と CPU の判定を組み合わせる。 |
| `rng-core` | 日時、キー入力、DS 設定などの値と、SHA-1・MT・LCG による計算を担う。現在ここにある GPU カーネルは、候補生成の呼び出し口を維持しながら整理する。 |
| `infra` | GPU デバイスの初期化、バッファと読み戻しなど、実行基盤を提供する。検索種別や GUI の状態には依存しない。 |

依存は GUI・CLI → `search` → `rng-core`・`infra` の方向にする。現時点で `rng-core` の GPU モジュールは `wgpu` と `infra` に依存している。GUI 側の呼び出し口が安定した後、移動による利点が確認できた段階でこの依存の分離を検討する。

## 入力・結果・エラー

GUI または CLI は選択値と文字列の変換を担当する。日時の範囲や DS 設定の整合性はドメイン層が検証する。例えば、カレンダー上正しい日付が Tepig の対象シーズンかどうかは `search` が検証する。

検索 API は構造化した結果を返す。表示用の日時とキー入力の書式、ソート、エクスポートの列は UI で結果を利用する段階で決める。入力、GPU、ワーカーの失敗は検索エラーとして返し、候補ゼロの正常終了と区別する。技術的な原因は診断情報として保持し、ユーザー向けの文言は呼び出し元で決める。

## 実行のライフサイクル

GUI は起動時に検索ランタイムを初期化し、複数の検索で再利用する。検索側は日付バッチの実行順と CPU ワーカーの終了を管理する。進捗は完了したバッチ数と重複排除後の候補数を返す。キャンセルは GPU バッチ間と CPU 候補処理中に確認し、実行中の GPU バッチと CPU ワーカーの終了を待ってから、キャンセルとして返す。

初回 GUI の実行結果は一括返却を前提とする。逐次結果、CPU フォールバック、SQLite、エクスポート形式の追加は利用要件に応じて決める。
